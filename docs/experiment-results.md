# Experiment: does a file-history index pay off?

Milestone 10 asks whether a small, persistent index makes
`GET /api/file-history` faster than traversing commits and trees on every
request, and at what cost. This page records one set of measurements and
what they show. No speedup was assumed in advance.

## Setup

- **Machine:** cloud VM, 4 vCPUs (Intel Xeon @ 2.10 GHz), Ubuntu 24.04,
  GCC 13.3, SQLite 3.45.1, local disk. Measured on 2026-10-23.
- **Build:** `-DCMAKE_BUILD_TYPE=Release`.
- **Command:** `history_benchmark --commits N --files 200 --repeats R` with
  N = 1,000 and 5,000 (R = 5) and N = 20,000 (R = 3). Each latency is the
  median of R runs, in-process (no HTTP), with a warm file cache.
- **Repository:** generated by the benchmark with the MiniGit++ library. The
  first commit adds 200 files in 20 directories; every later commit edits 1–3
  files, 80% of the edits going to 10 "hot" files. History is linear (one
  branch). The same seed gives the same repository.
- **Queries**, all from `HEAD`:
  - *hot file*: changed in roughly every fifth commit, with limit 20 and 1000;
  - *cold file*: added by the first commit and never changed again (the
    worst case for traversal, which must reach the root to find it);
  - *missing file*: a path that never existed.
- **"With index"** calls `file_history_with_index`, which opens the SQLite
  database read-only on every call, as the server does per request.

## What the measurements show

1. **Queries that make traversal walk the whole history get much faster.**
   A file that rarely changes, or does not exist, forces traversal to read
   every commit and the trees along the path back to the root: 0.7 s at
   20,000 commits, growing linearly. The index answers the missing file with
   one key lookup (about 0.1 ms at every size) and the cold file 30–50×
   faster.

2. **The index is not constant-time for rarely changed files.** Its cost for
   the cold file still grows linearly (0.7 → 4 → 18 ms), because rows from
   other branches are discarded by following `HEAD`'s first-parent line
   through the `commits` table down to each row's depth, one primary-key
   lookup per commit. That walk is about 40× cheaper than reading objects,
   but it is still a walk. A branch-independent ancestry test (for example
   skip pointers) would remove it; that was not implemented.

3. **Queries that stop early gain little.** For a hot file with `limit=20`,
   traversal only walks about 100 commits, which takes 3–6 ms at every size.
   The index *loses* ground as history grows (0.5 → 1.3 → 4.0 ms) because
   the query sorts every row for the path by depth (about 15,000 rows at
   20,000 commits) before returning the first 20. Keeping the depth in the
   `changes` key would let SQLite return rows already in order; not done.

4. **Long result lists gain about 10×.** With `limit=1000`, the index still
   reads each returned commit object for its metadata, which becomes the main
   cost (about 23 ms for 1,000 commits).

5. **A lagging index costs nothing extra but helps nothing.** After new
   commits, `HEAD` is not in the index and every query falls back to
   traversal at the same speed as without an index (differences in that
   table are noise). There is no partial use of a lagging index, so it only
   helps if `minigit index` runs after commits.

6. **Indexing cost.** Building takes about 0.13 ms per commit (2.6 s for
   20,000), mostly diffing each commit against its parent. Incremental
   updates cost about 0.2 ms per new commit (454 ms for 2,000) and do not
   read older history. Rebuilding from scratch takes as long as the first
   build.

7. **Size.** The index is about 46% of the size of the compressed loose
   object store. It stores ids as 40-character text and keeps a second
   B-tree on `commit_oid`; binary ids would roughly halve the id columns.

## When is the index worthwhile?

- **Yes** for a server answering many file-history queries over long
  histories, especially for files that rarely change, paths that do not
  exist, or requests with large limits: exactly the queries where traversal
  reads the whole history.
- **Hardly** for small repositories (below about 1,000 commits traversal
  answers in tens of milliseconds) or for "the last few changes of a busy
  file", which traversal already answers by reading a few dozen commits.
- **Only if it is kept up to date.** The index must be refreshed after
  commits (`minigit index`); otherwise requests fall back to traversal. They
  remain correct, just not faster.

## Limitations of this experiment

- One machine, warm cache, in-process calls; HTTP overhead and cold-cache
  disk reads are not measured. Timings on shared CI runners are noisier.
- Generated, linear histories with a simple edit pattern. Real repositories
  have merges, renames, larger trees and uneven directory structures; the
  equivalence tests cover branches and merges for correctness, but the
  benchmark does not measure them.
- Only first-parent file history is indexed. `changed-files` was not
  optimized and still traverses trees.
- Loose objects only. Real Git's pack files, commit-graph and changed-path
  Bloom filters address the same problem differently and are out of scope,
  so these numbers say nothing about real Git's performance.

## Reproducing

```sh
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release
for n in 1000 5000; do ./build-release/history_benchmark --commits $n --files 200 --repeats 5; done
./build-release/history_benchmark --commits 20000 --files 200 --repeats 3
```

`--keep DIR` leaves the generated repository in `DIR` for inspection with
`minigit` or real `git`.
